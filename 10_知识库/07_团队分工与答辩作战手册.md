## 三、5 分钟终期验收高光演示剧本

1. **前置准备（上台前 2 分钟）**：在 `system/` 执行 `./scripts/start.ps1`，浏览器打开 `http://localhost:5173`，确认顶栏响应流畅。
2. **第 1 分钟 · 三步约机时与冲突候补（`student` & `student2`）**：
   - 登录 `student`，在「仪器资源」选 `IY-001` 场发射电镜，展示未来 14 天半小时槽位 → 选明天 `09:00-10:00` → 填样品与经费卡 → 三步提交（状态变为 `待审批`）。
   - 退出换 `student2` 约**同一台仪器同一时段**，点击提交，界面立即提示**「已加入候补队列（`Waitlisted`）」**，直观证明同一时段绝不重复占用。
3. **第 2 分钟 · 机组审批与候补自动递补（`manager`）**：
   - 登录 `manager` 进入「预约工作台」，演示驳回 `student` 的预约并填写理由 → 展示系统在同一事务内释放时段，并自动将 `student2` 的候补单递补为 `已批准（待 5 分钟内确认）`，站内信实时送达。
4. **第 3 分钟 · 培训考核闭环与校外实名准入（新校外用户 + `admin`）**：
   - 在登录页切「校外用户注册」创建一个新企业账号 → 展示未审核前无法访问仪器 → 切 `admin` 在「用户审核」解密查看实名材料并批准 → 再展示「培训与资质」5 道安全考题（选第 `2, 1, 2, 3, 1` 项得 100 分）自动签发一年期资质。
5. **第 4 分钟 · 计费冲正、加密报告与安全审计（`manager` & `admin`）**：
   - 对一笔已完成预约展示秒级精确生成的费用单、执行一笔带理由的「费用冲正」（展示原始金额保留不变），上传一份 PDF 检测报告（展示 `SHA-256` 校验值），并在 `admin`「操作审计」展示完整留痕与 IP。
6. **第 5 分钟 · 三套口径绩效报表切换与 CSV 导出（`department`）**：
   - 登录只读监管账号 `department`，在「绩效报表」依次切换 **国家 50 万（3 台）→ 地方 20 万（4 台）**，展示 ECharts 双柱状图动态刷新与防公式注入的考核 CSV 一键下载。

## 四、高频尖锐追问「需求口径 + 代码实证」双层标准应答

### Q1：你们没有做问卷和一手访谈，怎么证明痛点和需求不是拍脑袋编的？
- **应答要点**：我们主动在开题报告 2.1.6 节写明了未做一手问卷的原因与局限（3 周窗口内小样本问卷无统计代表性，不造假数据）。需求可信度建立在三条硬证据上：① 六份国家与部委文件的考核指标与安全准入条款（白纸黑字要求逐次机时、对外机时、培训考核存档、检测数据归档）；② 四类既有系统的七维度公开手册比对（定位出候补、结算、资质、多口径、移动端五项共性断层）；③ 国家 50 万、地方 20 万、校内 40 万三份制度并排对照浮现出的多口径刚需。

### Q2：测试报告里写 500 并发 HTTP 压测 P95 是 `2225.68 ms`，没达到 NFR-01 的 `800 ms`，这算不算失败？
- **应答要点**（孙福泽/朱林立）：
  1. **最核心的数据正确性底线 100% 达成**：500 个真实 HTTP 请求同时争抢同一台仪器同一时段，结果精确为 `Pending = 1, Waitlisted = 499`，**超卖数为 0，错误数为 0**。
  2. **如实区分测试口径**：100 并发下 `P95 = 317 ms` 已在 800ms 内；500 并发 HTTP 测得 `2225 ms` 是在**单机 Windows + H2 文件/内存单实例 + 500 线程全部串行争抢同一把仪器行锁（100% 热点冲突极端工况）**下测得的端到端排队时间，而非分散在不同仪器上的常规并发。
  3. **工程诚实性**：我们不在报告里用拒绝请求或缓存假响应去凑 800ms 数字，而是保留真实压测 JSON（`docs/test-results/http-load.json`），并明确给出生产优化路径——部署到独立 MySQL 8 + Redis 锁快速失败返回 `409` 分流后，单请求锁等待开销可大幅下降。

### Q3：既然数据库已经有 `slot_claim` 复合主键了，为什么还要加仪器行锁、乐观锁和 Redis 锁？
- **应答要点**（朱林立）：单一主键约束只能保证最后 `INSERT` 那一下报错，挡不住业务层「先查槽位、判断进待审批还是进候补、分配排队号、写通知」这一整段临界区竞态；若只靠主键报错，后到的 499 个人会收到数据库冲突异常而非平滑进入 `Waitlisted` 候补队列。因此：Redis 锁负责多实例跨节点互斥，仪器 `FOR UPDATE` 行锁负责单库事务串行推进，`reservation.version` 乐观锁负责拦截并发状态修改，`slot_claim(instrument_id, slot_at)` 复合主键做最终物理兜底——四层各司其职。

### Q4：敏感数据和检测报告是怎么保护的？如果数据库被拖库会泄漏经费卡号吗？
- **应答要点**（许军/秦嘉玉）：不会明文泄漏。密码使用 `BCrypt` 慢哈希；联系方式、经费卡号/对公账户、校外用户实名核验材料以及上传的检测报告文件，在落盘前全部经 `CryptoStorage` 使用 **AES-256-GCM**（每次随机生成 12 字节 IV + 128 位完整性认证标签）加密，主密钥通过环境变量注入不进代码仓；报告下载时还会复核明文 `SHA-256` 摘要，底层文件哪怕被改动 1 个字节也会立刻拦截报警。

### Q5：学校如果已经有资产台账和统一身份认证，你们怎么对接而不是推翻重来？
- **应答要点**（秦嘉玉/朱林立）：代码里已经写好了三个标准对接切口（见 `IntegrationService.java` 与 `INTEGRATIONS.md`）：① 统一认证通过 `/api/auth/sso-ticket` 单次票据交换映射 `sso:{学工号}`，且生产模式下禁止校内角色用本地密码绕过 SSO，同时严禁 SSO 签发 `ADMIN` 权限；② 既有仪器台账通过 `/api/integrations/instruments` 幂等同步并打上 `source='external'` 只读锁，本地禁止篡改源头数据；③ 微信消息和上游结算回写采用本地 `integration_event` 事务外发箱（Outbox）+ `Idempotency-Key` 指数退避重试，外部系统宕机不影响校内正常约机和结算。
