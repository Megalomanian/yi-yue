# 一、立项依据与背景

## 1.1 行业现状与政策环境

大型仪器设备是高校开展高水平科研与研究生培养的物质基础。校内共享清单的口径并不统一，常见做法是把单价 40 万元以上、或虽未达到该金额但已列入清单的科研仪器纳入管理；国家层面的门槛则是单台套 50 万元及以上。这类设备分布在测试分析中心与若干学院的共用机组之中，前者承担公共测试服务，后者以学科自用为主、余量对外共享。两类机组在管理上的共同点是：设备价值高、单台机时有限、使用者跨院系甚至跨单位，因而"谁在什么时间用哪台仪器、用了多久、该收多少钱"这三个问题，构成了日常管理的主线。

从政策层面看，大型仪器开放共享已经由倡导性要求转为可考核、可追责的制度安排。2014 年国务院印发《关于国家重大科研基础设施和大型科研仪器向社会开放的意见》（国发〔2014〕70 号），明确单台套价值 50 万元及以上的科学仪器设备纳入统一开放的国家网络管理平台，并按 15 类分别管理；文件原文提出"推动非涉密和无特殊规定限制的科研设施与仪器一律向社会开放"。该意见同时要求建立评价体系与奖惩办法，由财政部门建立开放共享后补助机制。这一机制改变了高校的行为逻辑：设备买回来、账上有登记只是起点，还必须拿得出可核验的机时台账、对外开放机时与服务人次数据，数据不完整、口径不统一，会直接影响后补助申请与单位的考核结果。

具体的管理规则由《国家重大科研基础设施和大型科研仪器开放共享管理办法》（国科发基〔2017〕289 号）规定。该办法由科技部、发展改革委、财政部三家联合印发，就开放共享的组织管理、运行使用与共享服务提出要求，明确了管理单位、主管部门与相关部门的职责，也明确了仪器入网、信息报送、服务收费与绩效评价之间的衔接方式。对平台设计而言，这份文件的意义在于把"开放"从一句倡导拆成了可执行的动作：仪器要入网、信息要报送、服务要留痕，三者都需要系统承载。

考核环节的依据是《国家重大科研基础设施和大型科研仪器开放共享评价考核实施细则》。现行版由科技部办公厅于 2026 年 1 月印发，2026 年 2 月 1 日施行；此前的国科办基〔2022〕93 号版本已废止，现行版在官网上未标注发文字号，引用时只称文件全名。细则设组织管理、运行使用、共享服务 3 个一级指标、9 个二级指标，其中包含"年平均有效工作机时""年平均对外服务机时""在线服务平台可预约仪器比例"等可以直接落到数据字段的项；考核结果分优秀、良好、合格、较差四档，优秀与良好给予后补助，较差者限期一年整改，并在整改期内限制新购仪器。这里有一处关键限定需要说明：该考核的对象是中央级高校和科研院所，地方高校并不直接参加；但多数地方高校在制定校内办法时参照这套指标体系开展校内考核与自查，指标口径因此具有很强的传导性。对平台而言，按这套指标预留字段，等于同时满足上级考核与校内自查两种需要。

与开放共享并行的第一条约束线是科学数据。《科学数据管理办法》（国办发〔2018〕17 号）第二条把科学数据界定为"通过观测监测、考察调查、检验检测等方式取得并用于科学研究活动的原始数据及其衍生数据"。大型仪器的检测报告、原始谱图与导出数据正落在这一范围内，办法要求分级分类管理、完整归档、可追溯使用。这意味着检测数据不能只留在某位老师的个人电脑里，需要有统一的存放位置、明确的保存期限和可核查的访问记录。

第二条约束线是实验室安全。教育部办公厅《高等学校实验室安全规范》（教科信厅函〔2023〕5 号）把资质要求写得比较具体：第十条（二）规定，进入实验室的人员须先接受安全知识、安全技能和操作规范培训，考核合格方可进行实验操作；第十一条（四）要求对设备使用等标准操作规程进行培训和评估，并记录存档；第十七条要求取得准入资格后方可开展实验。三条合起来，构成"培训—考核—准入"的资质授权链条，每一环都要求留痕。在纸质条件下，这条链在人员更替、老师休假或跨机组借用设备时最容易断开，一旦发生设备损坏，学校很难证明当事人确实具备操作资格、授权也确实在有效期内。

国务院《关于加强数字政府建设的指导意见》（国发〔2022〕14 号）则从治理数字化的角度，要求面向师生的服务事项尽量线上化、标准化，减少纸质流转与重复填报。这一条为平台的形态提供了政策背景：把预约、审批、结算、报表从线下搬到线上，方向与政策同向，落地时也更容易得到管理部门的配合。

还有一处细节值得单独说明，它是本项目若干设计决定的直接来源：金额口径并不是一套。国家层面按单台套 50 万元及以上纳入统一开放平台；部分地方与省级平台按财政资金购置 20 万元以上纳入省级共享平台，各地门槛并不一致；校内共享清单则由各校自定，常见为 40 万元以上或列入清单管理。三套门槛同时有效，意味着一台 60 万元的液相色谱仪既要出现在国家口径的报表里，又要出现在校内清单的台账里；而一台 25 万元的设备在省级口径下需要上报、在校内口径下却可能不在清单之内；至于 40 万元到 50 万元之间的设备，则在校内表里有、在国家表里没有。三份不同层级的文件并排对照，这层关系就浮现出来了：同一批仪器要在不同口径下各算一遍，任何一次设备增减都要同步改三处。这不是管理者的惰性，而是口径本身的多重性所致，也因此，平台把口径做成了可配置项而不是写死的常量。

政策要求已经相当明确，落地情况却参差不齐。从竞品对照与公开资料看，尚未把整条链路打通的单位里，多数仍以即时通讯工具发布空档、以 Excel 记录台账、以纸质上机本登记使用，三类载体彼此不连通：群里的约定不进 Excel，Excel 里的时段不与上机本核对，上机本上的时长又要靠人抄进年度填报表格。也有一部分机组已经把个别环节搬到了线上，例如用在线表单收集培训报名、用共享文档登记机时，但这些尝试多是单点工具，与结算、考核之间没有数据通道，报名表单里的名单最后仍要人工誊写。政策要求的"台账可核验"，在这样一种分散记录的结构下不易真正成立。问题的症结不在某一台设备或某一位老师，而在于缺少一个把预约、上机、计费、统计串起来的统一载体。

## 1.2 现有管理方式的痛点

以下七项问题由政策文献、竞品对照与业务流程推演归纳而来。需要说明的是，它们描述的是环节之间衔接上的共性困难，而非对某一单位现状的整体判断：不同机组的管理成熟度差别较大，有的已自建了简易的线上登记，有的仍完全依赖纸笔，共同的困难集中在环节之间的衔接上。

第一，约机时依赖即时通讯工具，先后顺序缺少可核验的记录。在群里发布空档、学生按看到消息的先后回复，这套做法本身没有留下任何时间戳，谁排上、谁没排上，事后只能靠翻聊天记录判断。争议每次不大，累积起来消耗的却是师生之间的信任，也占用了机组老师本应用于测试的精力。更麻烦的是顺序不可复现：聊天记录可以截图，但截图的先后与消息到达的先后并不是一回事。

第二，台账分散、口径不一，时段冲突仍会发生。不同机组各管一摊，有的用 Excel，有的用纸质上机本，两处记录并存而没有统一的校验点。同一台仪器在同一时段被两个人约到的情况仍会出现，往往到了现场才发现撞车，只能由老师临时协调，把一方顺延到下午或第二天。对校外用户来说，一次顺延意味着样品前处理白做、当天往返的行程作废，而对机组来说则是一次说不清楚的失信。

第三，爽约缺少成本，名义利用率与实际利用之间存在落差。学生约了机时因实验未准备好而不来，机组老师按约定时间开机预热、准备耗材，最后空等半天。这个环节既不记录也不追责，爽约没有成本。填报时写下的利用率偏高，真实开机效率偏低，两者长期背离，反而削弱了考核数据的参考价值。

第四，结算依靠手算，计费口径至少有三重：按小时、按样品数、按校内校外两套价格，校外又按是否加急区分。月底结账时，老师把上机本上的记录逐条对照价目表，用计算器加总，再手写费用单。样品种类多、跨月结算时容易出错，出错后也难以复核，因为原始记录与计算过程不在同一处。费用构成对送样人往往是不透明的，多数人只留下“老师说多少就多少”的模糊印象。

第五，资质与授权链不完整。谁参加过安全培训、谁通过了操作考核、谁有资格独立操作某类仪器、资格何时到期，多数情况下只存在于机组老师的记忆中，或散落在几份培训签到表里。人员更替、老师休假或跨机组借用设备时，这条链就断了。安全规范要求的"培训—考核—准入"关系，在纸质条件下无法在被问到的时候即时出示，事故追溯也就失去了最基础的一环。

第六，考核数据依靠人工汇总。机时利用率、对外服务机时、服务人次这些字段平时没有结构化沉淀，按年度组织实施评价考核时，机组老师要翻出全年的上机本逐条录入 Excel，再做汇总与核对。中心管理人员的说法是："每年填考核表，机时利用率这一栏我要翻三本上机本，再对着 Excel 加，前后两三天。"这三两天并非创造性劳动，却恰好压在考核截止前的紧张时段，而且每次重算都可能得到略有差异的结果。

第七，多口径统计困难，这是七项问题中最容易被低估的一项。国家按单台套 50 万元、部分地方按 20 万元、校内清单常见按 40 万元，三套门槛同时有效，而仪器台账里往往只有一个"是否大型仪器"的布尔字段。机组与中心因此要为同一批仪器维护三份名单，年终分别出表：国家口径的表要按 15 类归口并统计对外服务机时，省级口径的表只关心财政资金购置的那部分，校内表则按院系与机组分摊。三份表的数据源相同、取数规则不同，人工维护时任何一处改动都要同步三次，漏改一次就会出现两份表对不上，而这恰恰是检查时最容易被追问的地方。平台如果只支持单一门槛，等于把这道手工工序原样搬到线上，痛点并没有消失。

上述七项问题指向同一个结构性原因：预约、上机、计费、统计四个环节分别由不同载体承载，环节之间靠人工搬运数据，任何一次搬运都可能失真。只把其中一环搬到线上，其余环节仍在纸面，问题会以另一种形式重现——预约上了线而结算仍靠手算，月底依旧要人工对账；计费上了线而资质仍是口头授权，安全追溯依旧无法成立。因此需要的是一个覆盖全环节、并且能按多套口径出数的平台，而不是若干个互不相通的小工具。

## 1.3 技术趋势与可行性

从技术条件看，本项目的实现路径是清晰的，所需组件均有成熟的开源实现，团队在课程中已系统学习并在实验中用过其中大部分。

前端采用 Vue 3 与 Vite 构建，移动端使用 Vant 4 适配微信小程序与 H5，PC 管理端使用 Element Plus，统计图表使用 ECharts。选择这套组合的理由是：送样人的核心动作发生在手机上（查机时、约机时、扫码签到），机组老师与管理人员的工作发生在电脑前（审批、结算、报表），两端共用一套接口但需要不同的交互密度。Vant 4 的组件粒度适合移动端的单列表单，Element Plus 的表格与表单能力适合管理端的批量操作。ECharts 用于机时利用率、对外共享机时占比等指标的可视化，其导出能力可满足考核表的附图需要。

后端采用 Spring Boot 3.2、MyBatis-Plus、Spring Security 与 JWT。选型考虑的是并发与事务：预约提交需要在一个事务内完成时段占用、状态流转与消息入队，Spring 的声明式事务与 MyBatis-Plus 的条件构造器可以较直接地表达这类逻辑；Spring Security 配合 JWT 承担六类角色的鉴权，越权校验可以集中在过滤器与注解两层完成。

数据层为 MySQL 8.0 主库、Redis 7 与 MinIO。MySQL 承担仪器、预约单、费用单、资质、信用分等结构化数据；Redis 用于热点时段缓存、分布式锁与候补队列，其有序集合结构适合按提交时间排序的候补排队；MinIO 存放检测报告与原始数据文件，按仪器编号与预约单号分层组织，便于按年度归档。部署采用 Docker Compose，学校私有云 2 核 4 G 起步，容器化使开发、测试与演示环境保持一致，也降低了课程结束后的交接成本。

有几项技术在项目中承担关键作用，值得单独说明。其一是二维码：每台仪器贴一枚固定二维码，送样人扫码后由后端校验"当前时段是否存在该用户的已批准预约"，校验通过才启动计时。这比让用户手动点击"开始使用"更难作弊，也不需要额外的硬件投入。其二是分布式锁：同一时段的预约提交在瞬时可能有多人竞争，仅靠数据库唯一索引会在高并发下产生大量失败重试，引入 Redis 锁把冲突挡在业务层，唯一索引作为最后一道防线。其三是定时任务：超时未签到判定、候补补位、资质到期提醒、报表预生成都依赖定时调度，这类任务对时间精度要求不高（分钟级），用应用内的调度器配合数据库状态字段即可，不必引入额外的中间件。

可行性还包括组织条件。测试分析中心与资产与实验室管理处对平台的诉求是明确的：前者需要减轻台账与结算负担，后者需要按时拿出考核数据。团队 6 人分工覆盖需求、架构、前端、后端、测试与文档，指导老师具备信息系统开发与评审经验。综合判断，在 12 周内完成核心用例是可实现的，但必须严格控制一期范围。

## 1.4 选题必要性与创新点

必要性可以从三个时间尺度来看。短期是日常运行：每周都在发生的抢时段、撞车、爽约、手算费用，需要一套比即时通讯工具更可靠的约定机制。中期是年度考核：机时利用率、对外开放机时、服务人次这些字段必须在平时就沉淀为结构化数据，年底才能直接导出而不是重新统计。长期是安全与责任：上机资质与授权记录需要可追溯，一旦发生事故，学校能够说明"谁在何时获得了什么资格、由谁授权、在哪个时段使用了哪台设备"。

与市面上可获得的四类方案相比，本项目的定位有明确差异。高校自建的开源预约系统通常只有日历排班，不涉及计费与资质；仪器厂商随设备交付的排机软件只管理本厂设备，跨机组无法汇总；第三方检测机构的委托单系统强在样品流转与报告签发，但计费按样品而非机时，与考核口径不一致；科研云平台的共享模块功能较全，但按院系定制、部署与维护依赖厂商，课程项目难以承接。这四类方案共同的缺口是：预约数据与计费数据、考核数据之间没有打通。

本项目拟在四个方面做出自己的处理。

其一，时段唯一性的三重保障。数据库层对"仪器编号 + 时段起始 + 时段结束"建唯一约束，业务层在提交前用 Redis 分布式锁锁定该仪器该时段的键，数据行上再加版本号做乐观锁。三层并非冗余：唯一约束保证最终不超卖，分布式锁把绝大多数冲突挡在写库之前、避免大量异常回滚，乐观锁处理锁过期与短事务交叠的边界情况。这一设计直接对应非功能需求中"同一时段绝不超卖"的要求，也是压测的重点。

其二，扫码签到与计时、计费的联动。签到不是独立的打卡动作，而是预约单状态机的触发点：扫码成功即进入"使用中"，系统记录起始时间；下机时按实际时长与适用价目生成费用单。这一条把"用了多久"从人工记录变为系统记录，从而使结算与考核使用同一份数据。

其三，候补队列的自动补位。时段已满时预约单进入候补状态，按提交时间排序；有人取消或审批驳回释放时段时，队列首位的预约单自动转为已批准并推送通知。这一机制针对的是"抢不到就放弃"的现状，使紧俏机时的分配更接近先来后到，而不是网速快慢。

其四，按考核口径预生成绩效报表。报表字段与开放共享评价考核的填报项对齐，按仪器、机组、院系三个维度汇总机时利用率、对外共享机时、服务人次，并支持在国家 50 万元、地方 20 万元、校内 40 万元三套口径之间切换后导出，同一台仪器不必重复建账。报表由定时任务在每月初预生成并缓存，避免考核季集中计算造成的响应延迟。

这四点合起来，构成的是"预约—上机—计费—考核"同源的数据链，而不是四个功能的并置。项目的价值不在于功能数量，而在于同一条数据在不同环节被反复使用而不需要人工转录。

# 二、软件需求获取

## 2.1 调研方法与过程

本项目没有采用大规模一手访谈与问卷作为需求获取的主要手段，原因有两个。其一是周期：项目总周期 12 周，需求阶段只有 3 周，而仪器机组的工作节奏受样品排期与教学任务牵制，短时间内约不到足够数量的机组老师。其二是样本：即便勉强发出问卷，回收量也难以支撑统计推断，反而会得到一批"看起来有数据、实际不成立"的结论。与其如此，不如把可以核查的二手资料做扎实，用资料之间的交叉印证来代替一次覆盖不足的调研。

据此，需求获取以四条线展开：政策与制度文献梳理、学术文献与技术资料研究、竞品与同类系统分析、公开数据与案例整理。下文逐条说明每条线的来源、方法和它对需求的实际影响，并在 2.1.6 交代这套方法的局限。

### 2.1.1 政策与制度文献

梳理了六份文件（见 1.6 节参考资料），从中提取出三类无法回避的约束。

第一类是台账的可核验性。《国家重大科研基础设施和大型科研仪器开放共享评价考核实施细则》设组织管理、运行使用、共享服务 3 个一级指标与 9 个二级指标，其中"年平均有效工作机时""年平均对外服务机时""在线服务平台可预约仪器比例"三项都需要逐台、逐时段的原始记录作为计算基础。也就是说，考核不是年底补一张汇总表，而是要求数据在平时就以结构化方式沉淀。这一条直接决定了平台必须把"每一次上机"作为一条记录保存，而不是只保存月度合计。

第二类是资质的授权链。教育部办公厅《高等学校实验室安全规范》第十条（二）要求进入实验室的人员先经安全知识、安全技能和操作规范培训，考核合格方可实验操作；第十一条（四）要求对设备使用等标准操作规程进行培训和评估并记录存档；第十七条要求取得准入资格后方可开展实验。三条合起来是一条"培训—考核—准入"的链，链上每一环都要求可追溯。这意味着资质不能只是一个布尔字段，必须有类别、发证时间、有效期和复训记录。

第三类是数据的归档义务。《科学数据管理办法》第二条把"通过观测监测、考察调查、检验检测等方式取得并用于科学研究活动的原始数据及其衍生数据"纳入科学数据范围，并要求分级分类管理、完整归档、可追溯使用。检测报告与原始谱图因此不能只留在某位老师的个人电脑里，平台需要承担存储与归档职责。

这三条约束分别落到 UC-11（考核报表）、UC-08（资质认证）、UC-07（结果交付）三个用例上，不是附加功能，而是政策要求的最小实现。

### 2.1.2 学术文献与技术资料

技术侧的资料主要解决两个问题：需求怎么表达，以及并发怎么控制。

需求表达方面，采用用例驱动的建模路径：先用参与者与用例界定系统边界，再用顺序图描述用例内部的交互，最后用分析类图把用例中的名词沉淀为实体、控制与边界三类对象。这套路径与 GB/T 8567-2006 对需求规格说明书的章节要求相容，也与 ISO/IEC 25010 对功能适合性与性能效率的划分方式一致，便于后续把非功能需求逐条对应到质量属性上。

并发控制方面，公开资料中针对"时段占用"这类资源预约问题，常见三类做法：数据库唯一约束、悲观锁、乐观锁（版本号）。三者的失效场景不同——唯一约束能挡住重复写入，但挡不住"先查后写"之间的窗口；悲观锁能挡住并发，但在长事务下会拖垮连接池；乐观锁在冲突率高时重试成本大。单机部署时三者选其一即可，但本项目按前后端分离与水平扩展的方式设计，多实例部署后进程内的锁失效，因此需要引入跨实例的分布式锁。综合这几点，最终确定"唯一约束 + Redis 分布式锁 + 乐观锁"三层叠加的方案（即 NFR-01 的技术依据），三层各自封堵不同的失效场景，而不是简单堆叠。

候补排队方面，公开资料中对"时段释放后如何补位"的处理有两种语义：按申请时间先到先得，或按优先级插队。前者公平、可解释，后者效率高但容易引发争议。考虑到机组与师生之间的信任关系，选择先到先得的队列语义，并在超时未签到时自动释放回队列（对应 UC-04）。

### 2.1.3 竞品与同类系统分析

选定了四类具有代表性的同类系统做对照：通用商品化仪器共享管理系统、高校自建的校级共享平台、科研院所的实验室信息管理系统（LIMS）、开源的实验室预约系统。对照维度取七个，覆盖从查机时到出报表的完整链路。

| 对照维度 | 商品化共享系统 | 校级自建平台 | 院所 LIMS | 开源预约系统 |
|---|---|---|---|---|
| 仪器台账与检索 | 普遍具备 | 普遍具备 | 普遍具备 | 部分具备 |
| 预约与冲突控制 | 普遍具备 | 普遍具备 | 部分具备 | 部分具备 |
| 候补排队 | 少见 | 少见 | 少见 | 少见 |
| 计费与结算 | 部分具备 | 部分具备 | 部分具备 | 少见 |
| 资质与培训 | 部分具备 | 部分具备 | 部分具备 | 少见 |
| 考核报表与多口径 | 少见 | 部分具备 | 部分具备 | 少见 |
| 移动端入口 | 部分具备 | 部分具备 | 少见 | 少见 |

对照结果呈现出明显的分布：台账与预约这两项各家都做，属于"必须有但不构成差异"的部分；候补排队、计费结算、资质管理、多口径报表、移动端这五项则是普遍薄弱环节。这解释了为什么不少单位明明已经上了系统，机组老师仍在用即时通讯工具做二次协调——不是系统不能用，而是系统只覆盖了链路的头一段，后面的环节断了，人只能自己接上。

这条结论直接决定了本项目的定位：不做又一套台账，而是补齐链路上后半段缺失的环节。相应地，13 个用例中 UC-04、UC-06、UC-08、UC-09、UC-11 五个用例承担了差异化职责，这也是后面章节把它们的验收标准写得比其他用例更细的原因。

### 2.1.4 公开数据与案例

公开渠道能查到的数据主要支撑一个判断：金额门槛不是一套，而是三套并存。

国家层面，国发〔2014〕70 号把单台套价值 50 万元及以上的科学仪器设备纳入统一开放的国家网络管理平台，并分为 15 类；部分地方与省级平台按财政资金购置 20 万元以上的口径建库；校内共享清单则由各校自定，常见为 40 万元以上或列入清单管理。三套门槛同时有效，其后果是同一台设备要出现在不同的名单里：一台 60 万元的液相色谱仪同时属于国家级与校级名单，一台 25 万元的设备在省级口径下要上报、在校内清单里却可能不在其中，而 40 万至 50 万元之间的设备则是"校内有、国家无"。

这个判断没有被任何一份文件直接写出来，是把三份不同层级的文件并排对照后才浮现的。它对本项目的影响很具体：平台如果把门槛写死成一个常量，就必然要维护两套台账；只有当口径成为可配置项、一台仪器允许同时携带多个口径标识时，才能做到一次录入、多表输出。这一条从最初的二期备选提前进入一期，直接对应 UC-11 的"支持三套统计口径切换导出"。

### 2.1.5 需求的推导与收敛

资料整理完成后，用一条统一规则把结论收敛为需求：一个候选需求进入一期，必须同时满足两个条件——有政策文件或文献的明确依据，且位于"预约—上机—结算—考核"这条主链上；只有单一来源支持、且实现成本高的，列入二期备选。

按此规则，最初从文献与竞品分析中列出的 19 个候选用例被合并、删减为 13 个。删掉的包括"仪器共享收益分配"（超出课程范围，且分账规则依赖学校财务制度）、"耗材库存管理"（与主链关联弱，属于另一套系统）、"设备采购论证"（数据来源不在平台内）。"按口径切换导出报表"原本列为二期，因三套门槛并存的证据较为充分，提前进入一期。"信用分与违约管理"则是从竞品对照的薄弱项中补回的——四类系统中只有一家做了，但它是解决爽约问题的唯一低成本手段，因此保留。

### 2.1.6 方法的局限与后续验证

必须说明这套方法的边界，否则结论会被高估。

第一，没有一手数据，痛点的强度无法量化。本文可以说"约机时依赖即时通讯工具"是一种普遍做法（有竞品分析与公开资料支持），但不能说"某校每年发生多少次时段冲突"，因为没有任何来源能给出这个数字。因此 1.2 节的七项问题只陈述现象与机理，不附带发生率。

第二，竞品分析基于公开的产品手册、演示视频与用户指南，未做真实环境下的深度试用，对"好不好用"的判断是间接的。表中"部分具备"的判定尤其需要保留，它可能低估也可能高估了实际能力。

第三，不同单位的管理成熟度差异较大，本文的结论对"已有系统但链路断裂"的情形最贴切，对"完全手工管理"或"已高度集成"的情形都未必适用。

针对以上三点，M2 阶段不安排大规模的一手调研，而以两种方式校准：一是持续更新竞品资料与政策文件，特别是考核细则指标口径的变化；二是在需求评审中引入外部视角，请指导教师与有仪器使用经验的同学校对痛点排序、结算字段与移动端使用场景是否成立，提出的问题按 SRS 的变更历史表逐条登记并给出处理结论。若后续取得一手数据，以一手数据为准并修订相关段落。这一安排写入开题报告 4.2 的 M2 阶段说明。

## 2.2 涉众分析与用户画像

系统涉众可归为六类角色，编号与职责在全文档中保持一致。

| 角色编号 | 角色 | 主要关注点 | 对系统的影响 |
|---|---|---|---|
| AC-01 | 送样人 | 能否快速看到可约时段、费用是否透明、结果何时可取 | 使用频率最高，决定系统的易用性底线 |
| AC-02 | 仪器负责人 | 审批负担能否减轻、上机记录是否可信、结算是否省事 | 决定系统能否真正替代现有台账 |
| AC-03 | 平台管理员 | 台账是否完整、计费规则能否配置、报表是否可导出 | 决定数据口径的统一程度 |
| AC-04 | 主管部门 | 考核指标能否按时取得、对外服务规模是否可核查 | 决定项目的立项价值与验收标准 |
| AC-05 | 校外用户 | 注册门槛、价格是否公开、送样与取报告是否便利 | 决定对外开放机时的增长空间 |
| AC-06 | 定时任务 | 触发是否准时、失败能否重试、状态是否一致 | 决定超时释放、违约判定、报表预生成的可靠性 |

三个典型用户画像由政策文件、竞品系统的公开用户手册与业务流程推演归纳而来，描述的是角色在业务中的处境与诉求，不是对具体个人的刻画。

画像一：研二年级的送样人。每周需要送 2 至 4 个样品做液相或电镜表征，实验节奏受培养方案与论文进度双重挤压。她的核心诉求是"在实验做得差不多的时候，能立刻知道后天下午有没有位置"，而不是提前两周规划。她对价格敏感但不精细，更在意"会不会白跑一趟"。她的障碍在于：群消息容易被刷走，私聊老师又怕打扰；改约时不好意思开口，宁可放弃。

画像二：电镜机组的仪器负责人。同时负责一台场发射扫描电镜与一台配套的离子溅射仪，每周固定两个半天对外开放。他的核心诉求是"把排机这件事从我的手机里拿出去"，以及"月底不要再手算费用"。他对新系统的容忍度取决于第一次使用的体验：如果审批一步能完成，他愿意用；如果需要在多个页面之间跳转，他会退回即时通讯工具。他的障碍在于：现有台账是他自己维护的，他担心系统记录与自己的记录不一致时无法解释。

画像三：中心平台管理员。负责全中心仪器台账、计费规则与年度考核填报。她的核心诉求是"口径统一"与"可导出"，尤其是考核季能直接生成符合填报格式的表格，并且能按不同口径各出一份。她的障碍在于：各机组历史数据的记录粒度不同（有的按小时、有的按半天），仪器在台账里又只有一个"是否大型仪器"的字段，需要在导入时做一次口径归一与清单拆分。

## 3.3 顺序图

预约申请与冲突校验的顺序图描述如下。参与者为送样人、预约界面、预约服务、锁服务、仪器时段仓储与通知服务。送样人在检索页选定仪器与时段后提交表单，预约界面先做前端必填校验，随后调用预约服务的提交接口。预约服务读取用户档案，校验上机资质有效期与信用分，两项任一不通过即返回带错误码的响应，前端据此定位到具体字段。校验通过后，预约服务向锁服务申请以仪器编号与时段起始时间为键的分布式锁，锁等待上限设为 2 秒；获取失败直接返回"系统繁忙"，不进入后续流程。持锁期间，预约服务查询该时段的占用记录并尝试写入预约单，数据库的唯一约束作为最后一道防线，若仍触发唯一键冲突则捕获异常并回滚。写入成功后，预约服务将预约单状态置为待审批，调用通知服务向仪器负责人推送待审批消息，通知失败不影响主流程，消息进入重试队列。最后释放锁并向送样人返回预约单号。

预约审批与通知的顺序图描述如下。参与者为仪器负责人、审批界面、审批服务、预约单仓储与通知服务。仪器负责人在待审批列表中打开一张预约单，界面展示送样人信息、样品数、检测项目与该用户的历史违约次数。负责人选择批准或驳回；选择驳回时必须填写理由，界面在理由为空时禁止提交。审批服务先校验该预约单当前状态仍为待审批，防止两人同时审批造成的重复处理，校验采用带版本号的条件更新，更新影响行数为零则返回"该预约单状态已变更"。状态更新成功后，审批服务写入审批记录，包括审批人、时间、结论与理由，随后调用通知服务向送样人推送结果。批准情形下，通知内容附带签到时间窗与二维码入口；驳回情形下，通知内容包含驳回理由与重新预约的入口。若该预约单来自候补队列的自动补位，审批服务还会检查队列中是否仍有等待者，若有则触发下一轮补位。

扫码上机与结算的顺序图描述如下。参与者为送样人、微信小程序、签到服务、预约单仓储、计时服务、结算服务与通知服务。送样人扫码后，小程序解析二维码得到仪器编号并调用签到接口，同时上送微信身份凭证。签到服务据此定位用户，查询该仪器在当前时间窗内的已批准预约单；查不到则返回无有效预约，查到则继续校验资质有效期与仪器状态。校验通过后，签到服务以条件更新将预约单状态由已批准改为使用中，写入实际开始时间与签到方式，并通知计时服务启动计时。计时服务按分钟累计，期间可在小程序端查询已用时长与费用预览。下机时，机组老师在管理端触发结算，结算服务读取计时记录，按 0.5 小时向下取整计算时长，匹配单价规则生成费用单，并将预约单状态置为已完成。结算服务随后调用通知服务推送费用明细，同时把机时数据写入统计库，供报表任务次日汇总。

超时未签到违约处理的顺序图描述如下。参与者为定时任务、预约单仓储、信用服务、通知服务与候补队列。定时任务每 5 分钟扫描一次状态为已批准且开始时间已过 15 分钟的预约单。对每一张超时预约单，定时任务先做一次条件更新，将状态由已批准改为已违约，更新成功者才继续后续动作，以此避免与用户恰好在此刻扫码签到产生竞争。状态更新成功后，定时任务调用信用服务扣减信用分，扣分值与违约类型相关，扣分记录写入信用流水并注明关联预约单号。随后，定时任务通知送样人违约结果与申诉入口，通知仪器负责人该时段已释放。若该时段启用了候补队列，定时任务将时段释放事件投递给候补处理逻辑，由后者取出队首预约单转为已批准并推送通知。整个过程在一个任务批次内完成，单条失败不影响同批次其他记录，失败记录在下一轮重新扫描。

分析类图从边界类、控制类与实体类三个层次刻画系统结构。边界类对应三类界面：移动端小程序界面（检索、预约、签到、结果查看）、PC 管理端界面（审批、结算、台账、报表）与对外开放接口（微信消息回调、对公转账核销回调）。控制类按用例簇划分，包括预约控制器、审批控制器、签到计时控制器、结算控制器、资质控制器、信用控制器、报表控制器与通知控制器。实体类抽取自领域概念，主要有仪器、机组、时段、预约单、费用单、用户、上机资质、信用流水、检测报告、维保记录与操作日志。实体之间的关系是：一个机组包含多台仪器，一台仪器拥有多个时段，一个时段可对应零到多张预约单（历史上被取消的单据仍保留），一张预约单最多对应一张有效费用单，一个用户持有多条上机资质与多条信用流水，一张预约单可关联一份检测报告。仪器与单价规则之间是多对多关系，通过"仪器—用户类型—价格"的关联实体表达，这一设计源自调研中发现的校内不同院系存在内部价差异的情况。

## 4.4 技术路线与系统架构

系统采用 B/S 结构、前后端分离，后端按 Controller–Service–Mapper 分层。前端分为两个工程：移动端使用 Vue 3 + Vite + Vant 4，编译为微信小程序与 H5 两种产物；管理端使用 Vue 3 + Vite + Element Plus，图表使用 ECharts。两端共用一套 RESTful 接口与一份接口类型定义，接口文档由注解自动生成，避免文档与实现脱节。

后端使用 Spring Boot 3.2 + MyBatis-Plus + Spring Security + JWT。Controller 层只做参数校验与响应封装，业务规则集中在 Service 层，Mapper 层通过 MyBatis-Plus 完成单表操作，跨表统计走自定义 SQL。鉴权在过滤器层完成令牌解析与基础校验，细粒度的越权判断（例如机组老师只能审批本机组预约）放在 Service 层，以注解加切面的方式实现，避免权限逻辑散落在各处。

数据层由 MySQL 8.0、Redis 7 与 MinIO 组成。MySQL 承载结构化数据，预约单表对"仪器编号 + 时段起始 + 时段结束"建立唯一索引，费用单表对预约单号建立唯一索引，保证一张预约单只有一张有效费用单。Redis 承担三类职责：热点时段列表的缓存、预约提交时的分布式锁、候补队列的有序集合。MinIO 按"年度/仪器编号/预约单号"的路径存放报告与原始数据，桶策略设为私有，下载通过后端签发的临时地址完成，地址有效期 10 分钟。

部署使用 Docker Compose，包含应用容器、MySQL、Redis、MinIO 与反向代理五个服务，学校私有云 2 核 4 G 起步。这一配置的资源余量不大，因此做了两项约束：报表不在请求线程内实时计算，由定时任务预生成并缓存；图片与文件不落应用服务器本地磁盘，一律进 MinIO。备份策略为 MySQL 每日全量加 binlog 增量，MinIO 每周全量同步至校内另一存储节点。

关键设计点有三处。第一处是预约提交的三重保障，前文已述，实现时把锁的粒度定为"仪器编号 + 时段起始时间"，锁超时设为 10 秒，业务执行超过 2 秒未完成则主动释放并回滚。第二处是状态流转的幂等，所有状态变更采用带版本号的条件更新，更新影响行数为零即视为状态已变更，直接返回冲突而不重试，防止定时任务与用户操作互相覆盖。第三处是统计与业务分离，机时数据在结算完成后写入统计表，报表只读统计表，不直接扫描预约单明细，以此满足 20 万条预约单/年规模下的报表生成时间要求。

## 4.5 质量保证计划

质量保证从过程与产品两方面着手，具体落实为五条。

需求评审方面，SRS 定稿前先做组内评审，再邀请指导老师评审。评审采用逐条走查方式，对每个用例检查前置条件是否可判定、异常流是否覆盖、业务规则是否可测。评审提出的问题登记在册，标注责任人与关闭时间，未关闭的问题不得进入设计阶段。

代码规范方面，采用 main/dev/feature 三分支模型，feature 分支合入 dev 前须通过 ESLint 与 Checkstyle 检查，且至少有 1 人完成 Code Review。评审关注三类问题：事务边界是否正确、异常是否被吞掉、权限判断是否遗漏。提交信息要求写明关联的用例编号，便于回溯。

测试策略方面，单元测试使用 JUnit 与 Vitest，覆盖率要求不低于 60%，重点覆盖计费计算、状态流转与冲突校验三类逻辑；接口测试使用 Postman 维护集合，随接口变更同步更新；并发压测使用 JMeter，模拟 500 并发提交预约，验证不超卖与 P95 响应时间。压测在 M5 阶段执行两轮，第一轮定位瓶颈，第二轮验证修复效果。

缺陷管理方面，缺陷统一登记在 GitHub Issues，按严重级约定响应时间：致命缺陷 24 小时内响应，严重缺陷 72 小时内响应，一般缺陷 168 小时内响应。每个缺陷须记录复现步骤、影响范围与关联用例，修复后由提出人验证关闭。

文档同步方面，文档与代码同仓管理，每次迭代更新 SRS 的变更历史表，接口文档随代码生成，数据库设计文档随表结构变更同步修改。交付前做一次文档与实现的一致性核对，重点核对用例编号、状态名与字段名。

## 4.6 风险识别与应对

项目识别出五项主要风险，按下表跟踪。

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 抢约并发导致超卖，上线即事故 | 中 | 高 | 三重锁 + 压测 500 并发 + 灰度上线 |
| 真实机时数据拿不到，验收时演示无数据 | 中 | 中 | 早期与中心签数据使用授权，准备脱敏样本数据 3000 条 |
| 校外用户支付对接复杂 | 高 | 中 | 一期仅做对公转账线下核销，二期再接口 |
| 组员课业冲突，进度滑期 | 中 | 中 | 每周站会 + 关键路径任务双人备份 |
| 需求蔓延（老师不断加功能） | 高 | 中 | 需求变更走变更单，M2 后冻结一期范围 |

除上述五项外，还有两项风险需要在执行中留意。其一是数据口径风险：各机组历史记录的粒度不同，有的按小时、有的按半天，导入统计库时若不做归一，报表数字会互相矛盾；同时三套金额门槛并存，若不在仪器主数据上同时保留多个口径标识，同一台仪器会在不同表里被算出不同结果。应对办法是在 M3 阶段先做一次历史数据抽样比对，确定归一规则并写入数据库设计文档。其二是演示环境风险：课程验收在现场网络条件下进行，微信小程序的域名校验与消息推送可能受限制。应对办法是准备一套 H5 版本作为备选入口，并在验收前完成一次断网条件下的降级演练，确保核心链路（检索、预约、签到、结算）在没有外部消息通道时仍可演示。
